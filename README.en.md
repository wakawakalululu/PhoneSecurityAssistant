# Phone Security Assistant

**Turn your Android device into a small SSH-accessible host.**

Phone Security Assistant runs a full `sshd` server (based on Dropbear) inside the app and also
provides `rsync`, `sftp` and `scp` services. Once the service is running, any
computer on the same network can log in with a standard SSH client, transfer
files, or run backups.

This repository is an **independently released modified fork**. On top of the
original features it adds:

- **Privilege modes**: app privileges (normal) / root privileges (su) /
  ADB privileges (wireless debugging)
- **Built-in terminal**: run commands inside the app with a selectable
  privilege mode and live output
- **frpc tunneling**: runs the official `frpc` to expose the local sshd port
  on a public server
- **Tailscale networking**: runs the official `tailscaled` to join your tailnet
- **Nezha monitoring**: runs the official `nezha-agent` to report device status
  to a Nezha dashboard
- **WebDAV file access**: read-only HTTPS WebDAV browsing in the Android system file picker through SAF; no system mount path is created

## About the project

Phone Security Assistant provides an `sshd` server with shell access and rsync and scp/sftp
services. The services are provided by:

- [Dropbear](https://github.com/mkj/dropbear) (this version: 2026.94)
- [rsync](https://rsync.samba.org/) (this version: 3.4.4)
- `sftp-server` from [OpenSSH](https://github.com/openssh/openssh-portable)
  (OpenSSH 10.4p1)

> **Note**: the app does **not** start an rsync daemon. Clients invoke the
> remote `rsync` over SSH (the usual `rsync -e ssh` usage).

Rsync-over-SSH transfers are initiated by a remote client. The read-only WebDAV
SAF provider is now compiled and packaged into the APK (HTTPS + Basic auth,
directory browsing and streaming file reads); interoperability with a live
WebDAV server has not been tested on a real device yet, and in-app sync jobs
are not implemented.

Service endpoints, credentials, privilege modes, auto-start and remote-tool
controls are configured in the app's Settings and management screens. Runtime
TOML/YAML files for frpc, Tailscale and Nezha are generated by the app; do not
edit them manually.

## Installation

- Option 1: use the build artifacts of this repository
  - The GitHub Actions workflow (`.github/workflows/build-apk.yml`) builds
    debug/release APKs: release is `PhoneSecurityAssistant-<version>.apk`, while debug is
    `PhoneSecurityAssistant-<version>-debug.apk`;
  - You can also download an APK from the Releases page of this repository
    (when the maintainer publishes one).
- Option 2: build it yourself, see [Building](#building).

Notes:

- The package is `com.tencentx.pinyin`; **debug builds use
  `com.tencentx.pinyin.debug`** and can be installed alongside the release.
- **Not compatible with the previous version** (different
  package and signature): it cannot be installed as an upgrade over it.
  Uninstall the old version first (its configuration will be lost).
- On first launch the app requests "All files access"
  (`MANAGE_EXTERNAL_STORAGE`). Granting it manually is required to use
  rsync/sftp on shared storage; without it only the app's own files directory
  is accessible.

### Android permissions

- `POST_NOTIFICATIONS`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_SPECIAL_USE`
  — required to run sshd as a foreground service (keeps it alive when the app
  is backgrounded).
- `RECEIVE_BOOT_COMPLETED` — start on boot (can be disabled in the settings).
- `MANAGE_EXTERNAL_STORAGE` — lets rsync/sftp access files on shared storage.
- `INTERNET` — network access.

## Quick start

1. **Start the service**: open the app → tap "Start". The notification shows
   the listening address (e.g. `*:2222`) and the main screen lists all IP
   addresses of the device.
2. **Configure port and auto-start**: "Settings → Dropbear SSH → Port" sets
   the listening port; the allowed range is **1024–32768** (default 2222).
   In "Settings → Startup" you can enable "start on device boot" and
   "start on app opening".
3. **Configure login methods** (can be combined):
   - System username + password: "Settings → SSH Login → System username /
     System password";
   - Single-use passwords: when enabled, the password is shown in the app
     when a login is attempted (valid once);
   - Public key login: import an `authorized_keys` file (from a file or an
     https URL) under "Settings → Authorized keys".
4. **Log in from a computer**:

   ```bash
   ssh -p 2222 <user>@<device-ip>
   ```

   The device IP is shown on the main screen (e.g. `192.168.1.100`).
5. **File transfer examples**:

   ```bash
   # rsync backup (over SSH)
   rsync -avP -e "ssh -p 2222" ./photos/ user@192.168.1.100:/sdcard/backup/photos/

   # scp a single file
   scp -P 2222 ./file.txt user@192.168.1.100:/sdcard/

   # interactive sftp
   sftp -P 2222 user@192.168.1.100
   ```
6. **Quick settings tile**: add the Phone Security Assistant tile from the system quick
   settings panel to start/stop the service with one tap.
7. **Start/stop by Intent** (optional; must be allowed in the settings first):

   ```bash
   adb shell am start -a com.tencentx.pinyin.fg.START
   adb shell am start -a com.tencentx.pinyin.fg.STOP
   ```

## Privilege modes in detail

Under "Settings → Privileges & Escalation" you can configure the
**privilege mode for SSH logins** and the **terminal privilege mode**.

### 1. App privileges (normal)

- All processes run with the **app's own UID** (a normal app).
- The app's private directory is accessible; after granting "All files
  access", shared storage (`/sdcard`, ...) is accessible as well.
- No root required; the safest mode (default).

### 2. Root privileges (su)

- How it works: the **login shell of sshd is set to the device's `su`
  binary**. Dropbear spawns every session (shell, `scp`, `sftp`, `rsync`)
  through `su`, so those sessions **run as root**.
- The `su` path is auto-detected, or can be set manually ("su path"). The
  auto-detection checks `/system/bin/su`, `/system/xbin/su`, `/sbin/su`,
  `/su/bin/su`, `/debug_ramdisk/su`, `/data/adb/ksu/bin/su`,
  `/data/adb/ap/bin/su`, `/data/adb/magisk/su`, and finally `su` on `PATH`.
- Magisk, KernelSU, APatch and SuperSU-style implementations are supported.
  On first use the root manager shows a grant prompt on the device — confirm
  it.
- "Settings → Privileges & Escalation → Detect root access" checks whether
  `su` is usable.
- The built-in terminal can also run commands with root privileges.
- ⚠️ In root mode an SSH session has full system privileges: use strong
  passwords or public keys, and only open the port on trusted networks.

### 3. ADB privileges (wireless debugging)

- How it works: **libadb** pairs with and connects to the device's own
  "wireless debugging"; commands then run as the adb `shell` user
  (uid 2000), **without root**.
- Pairing steps:
  1. Open "Settings → About phone" and tap "Build number" repeatedly to
     enable **Developer options**;
  2. Go to "Developer options → Wireless debugging" and turn it on;
  3. Tap "**Pair device with pairing code**" and note the **pairing code**
     and **pairing port** (and the IP, usually `192.168.x.x:xxxxx`);
  4. Back in Phone Security Assistant → "Settings → ADB Wireless Debugging", tap
     "**Pair using a pairing code**" and fill in the host
     address, the pairing port and the 6-digit code;
  5. After pairing, tap "Connect / status" to connect. The connection port
     defaults to `127.0.0.1:5555`; you can also use the IP/port shown on the
     wireless debugging screen.
- Notes:
  - Pairing/connecting happens on the device's loopback or LAN interface;
    keep the network available while doing this;
  - **After a reboot (or after turning wireless debugging off/on) you must
    pair again**, and the pairing port may change;
  - The adb `shell` user can run commands a normal app cannot (such as `pm`,
    `am`, `getprop`, parts of the system directories), but it is **not
    root**;
  - If you see "authentication failed, pair again", remove the pairing
    information and pair once more.

## Using the built-in terminal

- Entry point: "**Terminal**" in the main screen menu (or the TV buttons).
- Features:
  - Tap the mode button to cycle between **app / root / ADB** privileges
    (the current mode is shown at the top);
  - Enter a command and tap "Run": stdout and stderr are streamed live into
    the console;
  - "Stop" terminates the running command; "Clear" clears the output;
  - Use ↑ / ↓ to recall previous commands from the history;
  - Long-running tasks keep running in the background; check their state on
    the "Remote & monitoring" screen;
  - When a command finishes, its exit code is shown (ADB streams have no
    exit code and are treated as successful).
- Example commands:

  ```bash
  id                                     # show the identity of the command
  getprop ro.product.model               # device model (more useful in ADB mode)
  ip addr                                # network interfaces
  ps -A | grep dropbear                  # sshd process (more complete in root mode)
  ls -l /sdcard                          # shared storage
  frpc -c /data/data/com.tencentx.pinyin/files/tools/frpc.toml
  tailscale status
  nezha-agent -c /data/data/com.tencentx.pinyin/files/tools/nezha-agent.yml
  ```
- Notes: if root mode is selected but no `su` is found, a hint is shown; if
  ADB mode is selected without a connection, the app asks you to pair and
  connect on the "Remote & monitoring" screen first.

## Read-only WebDAV access

1. Open "Settings → WebDAV (read-only files)" and enter an HTTPS server URL and optional username/password.
2. In the system file picker, choose the "Phone Security Assistant WebDAV" root to browse directories and open files.

The provider exposes read-only `content://` documents through Android SAF. It does not create a `/mnt/...` mount, so command-line programs cannot use it as a local path. Upload, delete, rename and offline caching are not supported.

## frpc tunnel setup guide

Purpose: expose the local sshd port through a public server when you have no
public IP, so you can SSH into your device from anywhere.

### 1. Prepare a public frps server

- You need a server with a public IP (VPS/cloud instance).
- Install the **frp v0.65.0** `frps` server on it.
- Example server-side `frps.toml`:

  ```toml
  bindPort = 7000

  auth.method = "token"
  auth.token = "your-strong-token"
  ```

- Open the firewall for:
  - `7000/tcp` (the frp control port; must match the client's "server port");
  - the **remote port** you intend to use (e.g. `6000/tcp`).
- Start the server: `./frps -c frps.toml` (or set it up as a systemd service).

### 2. Configure frpc in the app

"Settings → frpc Tunnel":

| Setting | Description | Default |
| --- | --- | --- |
| Server address | IP or domain of frps. **Using the IP is recommended** (see FAQ) | empty |
| Server port | `bindPort` of frps | `7000` |
| Token | must match `auth.token` of frps | empty |
| Proxy name | a unique proxy name | `sshd4a` |
| Remote port | public port mapped to the local sshd port. **When empty it defaults to the local sshd port** | local sshd port |
| frpc executable path | usually empty (use the bundled/imported binary) | empty |

Then go to the "**Remote & monitoring**" screen:

1. Tap "Install" on frpc → "Download" (or "Import from file");
2. Tap "Start" to run frpc;
3. Tap "Log" to inspect the output (connection success, errors, ...).

The app generates `frpc.toml` (in the private `tools/` directory) like this:

```toml
serverAddr = "1.2.3.4"
serverPort = 7000
auth.token = "your-strong-token"

[[proxies]]
name = "sshd4a"
type = "tcp"
localIP = "127.0.0.1"
localPort = 2222
remotePort = 6000
```

### 3. SSH through the tunnel

```bash
ssh -p 6000 <user>@<public-server-ip>
```

Notes:

- The remote port must be free on the server and allowed through its
  firewall; some frps configurations use an `allowPorts` whitelist — make
  sure it includes your port;
- The token must match, otherwise the log shows an authentication failure;
- With "start automatically with the remote service" and "start the remote
  service together with sshd" enabled, frpc is brought up automatically.

## Tailscale networking guide

The app runs the official `tailscaled` + `tailscale` CLI (version 1.90.6) to
join your own tailnet.

### 1. Get an auth key

1. Log in to the [Tailscale admin console](https://login.tailscale.com/admin)
   in a browser;
2. Open **Settings → Keys** and click **Generate auth key**;
3. Choose one-off/reusable and ephemeral options as needed, then copy the key.

> URL: <https://login.tailscale.com/admin/settings/keys>

### 2. Configure in the app

"Settings → Tailscale Networking":

| Setting | Description |
| --- | --- |
| Start tailscaled automatically | start the daemon with the remote service |
| Auth key | the auth key from above; may be left empty when already logged in |
| Device name (hostname) | the name shown in the tailnet; optional |
| TUN mode (requires root) | off = userspace networking (no root); on = TUN mode (root) |
| tailscaled executable path | usually empty (use the bundled/imported binary) |

### 3. Usage

1. Go to "Remote & monitoring" → Tailscale: "Install" → "Download" to get
   the binaries;
2. Tap "Start" to run `tailscaled`;
3. Tap "**Connect**" (`tailscale up`, passing the auth key and hostname);
4. Tap "**Status**" (`tailscale status`) to see the result;
5. Tap "**Disconnect**" (`tailscale down`) when done.

The login state (`tailscaled.state`) and the IPC socket
(`tailscaled.sock`) are kept in the app's private directory, so the login
survives app restarts.

### 4. About the two modes

- **Userspace networking mode (default, no root)**
  - `tailscaled` is started by the app itself with
    `--tun=userspace-networking`;
  - outbound traffic can reach the tailnet through the local SOCKS5 proxy
    (`127.0.0.1:1055`);
  - when other devices connect to a listening port on this device's
    Tailscale IP (e.g. the sshd port), the connection is forwarded by
    `tailscaled` to the local port;
  - **no** system-wide VPN interface is created, so other apps on the device
    cannot transparently use the tailnet.
- **TUN mode (requires root)**
  - `tailscaled` is started through `su` and creates a real TUN interface;
  - the device joins the tailnet as a regular node, like on a desktop;
  - requires a rooted device (creating a tun device and changing routes
    needs system privileges).

Notes:

- If TUN mode is selected but no `su` is found, start-up fails with a hint
  (see "Privilege modes in detail");
- With a one-off auth key, a new key is needed to log in again;
- Running `up` twice on the same device normally reuses the node; if
  something looks wrong, `down` then `up` again.

## Nezha monitoring setup guide

The app runs the official
[Nezha monitoring agent](https://github.com/nezhahq/agent)
(`nezha-agent`, version v2.3.5) to report the device status to your Nezha
dashboard.

### 1. Get the dashboard address and secret

1. Log in to your Nezha dashboard admin panel;
2. Open the "Servers" page and add (or open) a server entry;
3. Copy:
   - the **dashboard address** (e.g. `demo.example.com:8008`, i.e.
     `host:port`);
   - the **secret** (`client_secret`, a long random string).

> See the Nezha project documentation for deploying the dashboard:
> <https://github.com/nezhahq/agent>

### 2. Configure in the app

"Settings → Nezha Monitoring":

| Setting | Description | Default |
| --- | --- | --- |
| Report automatically in the background | start the agent with the remote service | off |
| Dashboard address (host:port) | dashboard host and port | empty |
| Secret | the `client_secret` from the dashboard | empty |
| Use TLS | enable when the dashboard uses HTTPS/gRPC-TLS | on |
| Disallow remote command execution from the dashboard | safer default | on |
| nezha-agent executable path | usually empty (use the bundled/imported binary) | empty |

### 3. Generate the config and run

1. Go to "Remote & monitoring" → Nezha monitoring agent: "Install" →
   "Download" to get the binary;
2. Tap "Start": the app generates `nezha-agent.yml` like this:

   ```yaml
   server: "demo.example.com:8008"
   client_secret: "YOUR_CLIENT_SECRET"
   tls: true
   disable_command_execute: true
   ```
3. The agent keeps running in the background and reports device status
   (CPU, memory, network, ...) to the dashboard;
4. The log/report panel shows the live reporting activity and errors;
   "Clear log" wipes the output.

Notes:

- The dashboard address and secret must match the server entry in the
  dashboard, otherwise nothing shows up there;
- Keep "Use TLS" enabled when the dashboard uses HTTPS (recommended);
  with a self-signed certificate you may need to disable TLS temporarily or
  use a trusted certificate;
- "Disallow remote command execution from the dashboard" is enabled by
  default to protect the device if the dashboard is compromised; turn it off
  only when you really need remote execution;
- To keep reporting after a reboot, enable "Report automatically in the
  background" or "Start together with the sshd service".

## FAQ

**Q1: Why do downloaded/imported binaries require root?**

Android 10 and later **forbids an app from executing files in its own data
directory**. Only files installed in the system native library directory
(`nativeLibraryDir`, i.e. `jniLibs/<abi>/lib<name>.so` inside the APK) can be
executed directly. Therefore:

- official binaries packaged into the APK with
  `tools/fetch-go-binaries.sh` **run directly**;
- binaries obtained with "Download" or "Import from file" live in the app
  data directory and **can only run through `su` (root)**.

**Q2: Why should the frpc "server address" be an IP?**

The official Linux `frpc` is a pure Go program using Go's built-in DNS
resolver. On some Android environments it cannot read the system DNS
configuration (e.g. `/etc/resolv.conf`), so domain names fail to resolve.
**Entering the frps IP address directly** avoids the problem.

**Q3: Why does Tailscale TUN mode require root?**

TUN mode needs to create a `/dev/net/tun` interface and modify the system
routing table, which requires system privileges (`CAP_NET_ADMIN`) that a
normal app does not have. On non-rooted devices use the default **userspace
networking mode** (no root required).

**Q4: Why is the port limited to 1024–32768?**

Ports below 1024 are privileged ports a normal app cannot bind to. The app
validates the "port" input against `1024–32768` and refuses other values; for
special bindings use the extra command line options to pass `-p` yourself
(validated by dropbear; at your own risk).

**Q5: What other Android 10+ / modern OS restrictions apply?**

- Files in the app data directory cannot be executed (see Q1);
- Access to shared storage requires manually granting "All files access";
- Long-running background work requires a foreground service (the app does
  this; a permanent notification is shown);
- Wireless debugging pairing does not survive a reboot; pair again (see
  "Privilege modes in detail");
- On some vendor ROMs (e.g. Samsung) the battery usage must be set to
  "Unrestricted", otherwise the service may be killed.

**Q6: Root mode does not seem to work — what to check?**

1. Is the device actually rooted? ("Settings → Privileges & Escalation →
   Detect root access");
2. Did the root manager prompt appear, and was it granted?
3. If `su` is not in one of the well-known locations, set the full path in
   "su path" manually.

**Q7: Why can't this app be installed over the previous version?**

The old and the new version use different package names and signatures — they
are two separate apps. Uninstall the old one first (its configuration is
removed as well).

**Q8: What happens when the frpc "remote port" is empty?**

It defaults to the **local sshd port** (e.g. 2222 as well). If you want the
public port to differ from the local one, fill it in explicitly.

**Q9: The service fails to start or the port is in use?**

- Check the listening address on the main screen / in the notification;
- Try another port (within 1024–32768);
- Check whether another app occupies the same port.

## Security notes and disclaimer

- sshd listens on all interfaces (`*:port`) by default. Only enable it on
  **trusted networks** — never on public Wi-Fi; use a firewall/VPN if
  needed.
- Prefer **public key login** and a strong password; disable authentication
  methods you do not need (the app warns when all of them are disabled).
- **Privilege modes (root / ADB) give sessions elevated privileges** — these
  are advanced features:
  - in root mode an SSH session *is* root; anyone who can log in owns the
    device;
  - ADB mode has the capabilities of the `shell` user (it can run `pm`,
    `am`, etc.);
  - evaluate the risk yourself and accept the consequences.
- Disclaimer: the software is provided "as is"; the authors are not liable
  for any data loss, damage or security problem caused by using it
  (especially the privilege features). Back up your data before use.

## Building

### Requirements

- Android SDK (`compileSdk 36`) with `ANDROID_HOME` set;

### Local build

- See `BUILDING`, `BUILDING-SIGNING`, etc. for environment setup;
- the convenience script `build.sh` (needs `ANDROID_HOME` and `sdkmanager`)
  runs the native prebuild scripts and then a release build;
- to package frpc / Tailscale / the Nezha agent into the APK, run
  `tools/fetch-go-binaries.sh` **before** the Gradle build (see below);
  skipping it still yields a working APK — the missing binaries can be
  downloaded or imported in the app's "Remote & monitoring" screen:

  ```bash
  # prebuild (called by the script automatically)
  app/src/main/cpp/prebuild-rsyn.sh
  app/src/main/cpp/prebuild-dropbear.sh

  # optional: download the official Go helper binaries for the APK
  # (not called automatically by build.sh)
  tools/fetch-go-binaries.sh armeabi-v7a arm64-v8a x86_64

  # debug / release
  ./gradlew assembleDebug      # output: app/build/outputs/apk/debug/PhoneSecurityAssistant-<version>-debug.apk
  ./gradlew assembleRelease    # output: app/build/outputs/apk/release/PhoneSecurityAssistant-<version>.apk
  ```

- Release signing is configured via `Sshd4a.properties` / a keystore (see
  `BUILDING-SIGNING` and the comments at the top of `app/build.gradle`);
  without it the release APK is built unsigned.
- ABIs:
  - release: `armeabi-v7a`, `arm64-v8a`, `x86_64`;
  - debug: `x86_64`, `x86` (convenient for emulator testing).

### Packaging the official frpc / Tailscale / nezha-agent binaries

`tools/fetch-go-binaries.sh` downloads the official release artifacts for
**frpc v0.65.0**, **tailscale(d) 1.90.6** and **nezha-agent v2.3.5**, and
places them as `app/src/main/jniLibs/<abi>/lib<name>.so`, so they are
installed into the native library directory and can be executed directly.

```bash
# default: arm64-v8a (the only ABI usable on real devices)
tools/fetch-go-binaries.sh

# multiple ABIs (significantly larger APK; mainly for emulators/tests)
tools/fetch-go-binaries.sh arm64-v8a x86_64

# force a re-download
tools/fetch-go-binaries.sh --force arm64-v8a
```

Notes:

- `app/src/main/jniLibs/` is listed in `.gitignore`: the official binaries
  are **not committed** to git;
- debug builds may not contain these binaries; in that case use
  "Remote & monitoring → Install → Download / Import from file"
  (imported binaries require root to run, see FAQ Q1);
- frp v0.65.0 has no 32-bit x86 (`386`) build, so `libfrpc.so` is skipped
  for the `x86` ABI.

### CI build

- The workflow `.github/workflows/build-apk.yml` downloads helper binaries
  for `armeabi-v7a`, `arm64-v8a`, `x86_64` and `x86` by default (upstream frpc
  has no x86 build), then builds debug/release APKs on GitHub Actions.
- Release APKs are named `PhoneSecurityAssistant-<version>.apk`; debug APKs are named
  `PhoneSecurityAssistant-<version>-debug.apk`. When the repository secrets
  (`KEYSTORE_BASE64`, ...) are configured the release APK is signed (see
  `BUILDING-SIGNING`), otherwise it is unsigned. Pushing a `v*` tag also
  creates a GitHub Release with both APKs attached.
